# なぜ5W1Hはソフトウェアアーキテクチャで破綻するのか――そして何が有効なのか

多くのアーキテクチャ文書は、日常的な説明の習慣をそのまま引き継いでいます。5W1Hです。誰が・何を・いつ・どこで・なぜ・どうやって。人間が物語として語るときの型なので、「漏れなく書けた気」になりやすい。

しかし実システムでは、この習慣がじわじわと疲労を生みます。文書が増え、図が増え、すり合わせ会議が増える。人が不注意だからではありません。座標系が不安定だからです。同じ事実が複数の箱に落ち、1つの変更が全体の書き換えを誘発します。

本稿の主張は単純です。5W1Hは便利な語りの足場であって、複雑なシステムの構造基盤にはなりません。動的で分散し、運用責任が問われるシステムには、別の最小要素が必要です。三つの一次独立な軸――構造（Structure）、ダイナミクス（Dynamics）、観測（Observation）――そして、それらを「どう見るか」を定める方法としてのViewです。

---

## 1. 5W1Hは語りには強いが、構造には弱い

5W1Hは、人に状況を説明するには有用です。網羅しやすく、説明の抜けを減らします。けれども、直交するモデルのようには振る舞いません。カテゴリ同士が独立ではなく、システムが変化すると合成が破綻します。

アーキテクチャで起こる破綻は、だいたい同じ形をします。

第一に、カテゴリが重なります。「Who（誰が）」は責任境界を暗に含み、それが「What（何を）」を形づくり、さらに「How（どうやって）」を制約します。「Where（どこで）」はレイテンシや障害ドメインを含意し、「When（いつ）」と「How（どうやって）」を書き換えます。整った5W1Hの文章を書けても、同じ情報が別の見出しで再登場することは防げません。

第二に、粒度が漂います。ある「What」はAPIエンドポイントで、別の「What」はサブシステム全体です。ある「When」は夜間バッチで、別の「When」はイベント駆動の状態遷移です。5W1Hはレベル整合を強制しないため、文書がミクロと俯瞰の間を予告なく往復します。

第三に、時間が過小記述になります。「When」は振る舞い（behavior）そのものではありません。実システムは順序、分岐、リトライ、冪等性、タイムアウトを要求します。これは付け足しではなく、システムそのものです。

第四に、観測が後回しになります。5W1Hには「どう知るか」の明確な居場所がありません。ログ、メトリクス、トレース、SLO、アラート方針は、主要カテゴリに要求されないため後付けになりがちです。

結果は予測可能です。文書は大きくなるのに脆い。変化で劣化し、編集のたびに整合性が脅かされます。

## 2. 実務での破綻パターン

これは哲学の問題ではありません。運用の問題です。

### 2.1 真実が複数箇所に重複する

典型的なアーキテクチャ一式には次が含まれます。

- コンポーネント図（誰が誰と話すか）
    
- シーケンス図（どの順序か）
    
- 運用手順（壊れたとき何をするか）
    
- ダッシュボード説明（何を見るか）
    

どれも正当です。問題は、同じ事実を異なる語彙と暗黙の前提で言い換え、時間とともに乖離することです。複数の「真実」を、記憶と会議で突き合わせる羽目になります。

### 2.2 組織変更が技術的意味を塗り替える

チーム境界やオーナーが変わると、5W1H型文書は「Who」が「What」や「How」と絡み合っているため、あちこちの修正を強要します。アーキテクチャ自体は変わっていないのに、座標系が変わったせいで文書は全面改稿になる。意味は同じなのに、文章だけが書き換えられる。この隠れコストは大きい。

### 2.3 「Why」が「What」に溶けて消える

5W1Hは「何を作ったか（what we built）」と「どう動くか（how it works）」に誘導します。その結果、設計意図――トレードオフ、制約、代替案――が「What」の説明に溶け、数カ月後には意思決定が回収できない。システムは存在するのに、理由は蒸発している。

これは最も高価な損失の一つです。再審議（re-litigation）を招き、当時の成立条件を壊す「最適化」を誘発します。

### 2.4 自動化が失敗する（機械可読な構造がない）

多くのチームは、何らかの形で「Architecture as code」を望みます。図の生成、設定の検証、再現可能なデプロイ、契約の強制。ところが5W1Hは人間向け分類であり、型付きモデルではありません。言語が曖昧で粒度も不統一なので、信頼できるツールに落ちません。

機械検査できないアーキテクチャは、退行防止を文化に依存します。それは持続しません。

## 3. 安定な基盤：構造・ダイナミクス・観測

工学の多くの分野で、複雑な人工物は繰り返し三種類の記述に収束します。

- 何が存在し、どう配置されているか
    
- 時間とともにどう変化するか
    
- どう観測され、どう判定されるか
    

これは次に対応します。

- 構造（Structure）
    
- ダイナミクス（Dynamics）
    
- 観測（Observation）
    

これは「新しいフレームワーク」というより、構築・運用・検証が必要なときに何度も再発見される最小の座標系に近いものです。

### 3.1 構造（Structure）

構造は、存在物と接続の静的レイアウトです。

例：モジュールやサービスの依存、データ構造とスキーマ、ネットワークトポロジと障害ドメイン、信頼境界とインターフェース。  
構造は「部品は何か」「境界はどこか」「何が何を参照するか」に答えます。

### 3.2 ダイナミクス（Dynamics）

ダイナミクスは、時間の中での変化です。

例：シーケンスと因果フロー、状態機械と遷移、リトライやタイムアウトやバックプレッシャ、周期処理とイベント駆動スケジューリング。  
ダイナミクスは「次に何が起きるか」「どの条件で分岐するか」「次の一手が成立するために何が真であるべきか」に答えます。

### 3.3 観測（Observation）

観測は、システムを読める状態にする仕組みです。

例：ログ、メトリクス、トレース、アラート、SLO、ヘルスチェック、検査点、バリデーションゲート、成功・失敗・復旧の証拠。  
観測は「何が分かるか」「いつ分かるか」「十分な証拠とは何か」に答えます。

本稿の重要な主張は、観測は任意ではないという点です。現代のシステムは計算だけでなく可観測性によって定義されます。「どう知るか」が欠けているアーキテクチャは未完成です。

## 4. 5W1Hを三軸に写像する

5W1Hが「間違い」になるわけではありません。「派生」になります。5W1Hの各要素は、三軸への部分射影として扱えます。

|5W1H要素|主写像|役割|
|---|---|---|
|What / Where|構造|存在、配置、接続|
|When|ダイナミクス|タイミング、順序、条件、周期性|
|How|ダイナミクス / 観測|制御ロジックと検証のされ方|
|Who|構造 / View|責任境界とアクセス範囲|
|Why|制約（全軸に作用）|要求、トレードオフ、意図、禁止|

ここで重要な注記が二つあります。

第一に、「Why」は同格カテゴリではなく制約（Constraints）として扱うほうがよい。意図と制約は第4軸ではなく、全軸の選択を縛ります。制約は、システムにおける「物理法則」に近い。全軸に作用する意味論的な地盤です。物理世界に触れるシステムなら、空間排他性や時間因果性のような不変量がここに入ります。ソフトウェアなら、整合性モデル、安全制約、交渉不能なインターフェース契約として現れることが多い。要するに、制約は構造とダイナミクスにおける許容（admissible）を定め、観測における最小要件を定めます。これがあって初めて、そのシステムを信頼できます。

第二に、「Who」は本質的に曖昧です。組織責任を指すこともあれば（構造境界）、視点・権限・露出を指すこともある（Viewの問題）。これを単一の箱に押し込めることが、5W1Hによる文書 churn の大きな原因です。

## 5. View：成果物を投影として扱う（別の真実にしない）

安定な基盤を受け入れると、単なる文書の束より有用な概念が定義できます。Viewです。

Viewは追加情報ではありません。目的と制約により形づくられた、構造・ダイナミクス・観測の選ばれた投影です。

これにより、馴染みの成果物はこう再解釈できます。

- コンポーネント図は、構造を強調するView
    
- シーケンス図は、ダイナミクスを強調するView
    
- ダッシュボードは、観測を強調するView
    
- ランブックは、復旧制約のもとでダイナミクスと観測を組み合わせたView
    

重要なのは、Viewが独立した真実になってはいけないことです。Viewは、基盤から再生成できるか、少なくとも基盤に対して妥当性検証できる投影であるべきです。

ここから実務的な設計規則が得られます。  
アーキテクチャ文書が腐るのは、人が怠惰だからではない。Viewが独立した真実として扱われ、互いに漂流するからだ。

Viewとして扱うと、整合性について次の問いが立てられます。

- このViewはどの軸に依存しているか
    
- どの制約を前提としているか
    
- どの証拠を要求しているか
    
- 何が安定でなければ、このViewは有効でなくなるか

## 6. なぜソースコードもViewなのか

エンジニアはコードを「真実」と見なしがちです。部分的には正しく、部分的には危険です。

ソースコードは、特定の言語で構造とダイナミクスを表現するViewです。強力ですが不完全です。多くの場合、レビュー可能な観測モデルを明示的に含みません。何をログに残すか、何を測るか、何が失敗か、復旧判断をどう下すか。

このことが、よくある運用上の痛みを説明します。  
コードが唯一の真実になると、観測は後付けになる。

その結果、チームはコードを読み、意図を復元し、制約を推測しながら可観測性を作り直す。これはインシデントのたびに繰り返されます。

Viewベースのアーキテクチャで目指すのは逆です。コードは中心に置きつつ、観測と運用上の証拠を第一級のViewとして扱い、同じ基盤にアンカーする。そうすれば、他のViewが安定することでコードも読みやすくなります。

## 7. 全部を書き換えずに導入する方法

文書をゼロから作り直す必要はありません。座標系は段階導入できます。

### 7.1 既存成果物をViewとして棚卸しする

いまあるものを列挙します。図、文書、ランブック、ダッシュボード、デプロイ設定。  
それぞれに対し、どの軸を強調しているか（構造・ダイナミクス・観測）、目的は何か、どの制約を前提にしているかを付与します。これだけで、重複と欠落が見えます。

### 7.2 軸ごとに欠落を見つける

よくある欠落は次です。

- 構造はあるが、ダイナミクスが暗黙（「動くはず」）
    
- ダイナミクスはあるが、観測がない（証拠がない）
    
- 観測はあるが、拠り所がない（重要モデルがなくアラートが漂う）
    

これは文書の欠陥ではなく、アーキテクチャの欠陥として扱うべきです。

### 7.3 可能なら軸ごとに単一の真実を選ぶ

真実の置き場を決めます。

- 構造：OpenAPI、スキーマ、依存マニフェスト
    
- ダイナミクス：状態機械、ワークフロー仕様、テストされたシーケンス
    
- 観測：テレメトリ仕様、SLO定義、証拠ポリシー
    

その上で、文章や図はそこから派生するViewとして扱う。完全な自動生成でなくても、参照リンクやチェックリストだけで漂流は減ります。

### 7.4 View整合をレビュー質問で守る

軽量なレビュー設問に落とせます。

- 構造の変更は何か
    
- ダイナミクスに何を導入・変更したか
    
- 失敗検出と成功検証に必要な観測は何か
    
- 更新が必要なViewはどれか。再生成できるViewはどれか
    

これにより「文書作法」は、工学的ワークフローになります。

## 8. 得られるもの

### 8.1 変更が局所化する
組織境界が変わっても、基盤が安定なら影響は限定できます。組織視点に依存するViewだけを更新すればよく、全体の語り直しを避けられます。

### 8.2 可観測性が「装飾」ではなく「構成要素」になる
観測が後付けではなく、最小記述の一部になります。失敗が不可避で復旧を設計する現実運用と整合します。

### 8.3 ツール化が現実的になる
軸の所属が言えれば、検証や再生成が可能になります。チェッカーやレポートで退行から守れます。

### 8.4 レビューが単純になる
文体ではなくモデルを議論できます。構造は整合しているか。ダイナミクスは安全で完備か。観測は運用に十分か。Viewは対象読者に適切な投影か。労力が調整から工学に戻ります。

## 結び

5W1Hは会話で説明するには優れています。しかし、アーキテクチャの安定な座標系にはなりません。

複雑で変化し、運用責任が伴うシステムに必要な最小の基盤は次です。

- 構造（Structure）
    
- ダイナミクス（Dynamics）
    
- 観測（Observation）
    

そして、コミュニケーションの実務方法は次です。

- Viewは投影であり、別の真実ではない
    

これは新しい方法論を発明する話ではありません。漂流が見える座標系を採用し、変化を扱いやすくし、証拠を第一級にする話です。

人が努力しても文書が腐るなら、それは努力不足のサインではありません。座標系が不安定だという信号です。基盤を直し、その上にViewを定義してください。

---

以下の図は、三軸とViewの関係を要約します。

```
      Observation (O)
            ^
            |
            |
            |
            +--------> Structure (S)
           /
          /
         v
    Dynamics (D)
```

Viewは、目的と制約で定義される、三軸（Structure/Dynamics/Observation）からの投影である。  
Observationは証拠（evidence）を生成し、その正当性を支える役割を持つ。一方、Viewはその証拠（および三軸の内容）を、特定の目的と読者に合わせて選び、提示する役割を持つ。
