# 制約下のトリアージとしての設計

## 1. 事故は設計を可視化する

蒸気機関の歴史は、発明家と機関の物語として記憶されがちである。だが、安全な蒸気利用は、発明だけによって築かれたわけではない。そこには、繰り返し起きた事故があり、設計 製作 検査の規則があり、被害が拡大する前にどこで仕事を止めるべきかを決める規律があった。アメリカでは、1905年のグローバー靴工場の災害を含む一連のボイラー爆発事故が、1910年代の最初の ASME Boiler Code の整備を後押しした。ASME 自身も、このコードを反復する失敗への応答であり、設計 製作 検査のための正式な規則群として位置づけている。

この歴史がここで重要なのは一つの理由による。工学は、発明の場面だけでなく、ローカルな慣行だけでは足りなくなる失敗の場面でこそ姿を現す、ということを示しているからである。コードとは、事後的にベストプラクティスを書き留めた記録にとどまらない。それは、何を進めてよいか、何を確認すべきか、どこで止めるべきかを決める仕組みである。本稿はこの観察から出発する。

## 2. このエッセイが付け加えるもの

前のエッセイは、説明だけでは足りなくなったときに必要になる操作語彙として、execution judgment gate evidence contract を立てた。そして、仕事が統治可能になるのは、comparability が保持され、前提が崩れたときに停止でき、判断が basis を失わずに境界を越えられるときだけだと論じた。ここで本稿が問うのは別の問いである。そうした区別が立ったとして、設計は制約の下で実際には何を配分しているのか。

私の答えは、設計は verification resources を配分している、というものである。配分されるのは、注意力、レビュー時間、計算資源、承認権限、再実行コストである。設計は、それらの資源をどこで厚くし、どこで薄くでき、どこで仕事を暫定のままに留め、どこではまったく進めてはならないかを決める。その意味で、設計は単なる「制約下の意思決定」ではない。設計とは、制約下のトリアージでもある。

## 3. トリアージとは配分である

ここでいうトリアージは、救急医療そのものを指しているのではない。希少性の下での規律ある配分を指している。工学的な仕事において希少なのは、たいてい行動の候補そのものではない。希少なのは、信頼できる比較、再演可能な basis、利用可能なレビュアー、安全に止められる地点である。だから設計は、最適化より前に始まる。チームが最善の解を選ぶ前に、何が安定した条件の下で admissible なのか、何がまだ provisional なのか、何を次の段階の外に残すべきかを決めなければならない。

第一のエッセイは、5W1H は叙述には有効だが構造としては弱く、より安定した基底には Structure Dynamics Observation が必要であり、View は独立した真理ではなく projection として扱うべきだと論じた。そこでは Observation は任意ではなかった。どう知るかは、システムが何であるかの一部だからである。第二のエッセイは、仕事を再実行し、確認し、停止し、正当化し、境界を越えて受け渡す必要が生じた時点で、説明だけでは足りず、より豊かな操作語彙が必要になると論じた。本稿はそこにさらに一段を加える。すなわち、それらの操作上の区別が実務の中で機能し続けるために、希少な verification resources がどのように配分されているかを問う。

## 4. 検査はすでにトリアージの理論を含んでいる

これを実際に見るには、検査の仕事がわかりやすい。検査には、静かなトリアージの理論がすでに含まれている。重い工程が始まる前に、誰かが basis と段取りと許容条件を確認し、どの地点で仕事を続けてはならないかを確かめる。工程の途中では、誰かが動き、ドリフト、異常な揺れ、負荷の挙動を監視し、その工程がまだ可逆であるあいだに異常を見つけようとする。工程のあとでは、誰かが起きたことを見直し、basis がどこで破綻したか、比較がどこで不正当だったかを特定し、場合によっては標準そのものを改訂すべきかを判断する。これは本体業務の外側に付く装飾ではない。時間軸に沿って verification resources を配分すること自体が仕事なのである。

その配分は phase ごとに変わる。pre-process で希少なのは speed ではなく admissibility である。問われるのは、高価な仕事をそもそも始めてよいかどうかだ。注意力は、コストが広がる前に baseline 確認、条件確認、停止権限の設定へ使われる。in-process で希少なのは reversibility である。監視の注意力と異常停止の権限が重要なのは、補正がまだ下流の手戻りより安いからである。post-process で希少なのは replayability である。レビュー時間、保存された記録、改訂に使う労力は、後の判断が記憶だけから始まらないように配分される。

要点は、工学が文字どおり検査であるということではない。検査という実務が、judgment と execution が時間軸の中でどのように分業するかを、すでに見える形にしているということである。

|Phase|現場像|判定側|実行側|設計上の問い|
|---|---|---|---|---|
|Pre-process|段取り確認|比較の basis を固定する|実行を開始してよいかを確認する|この仕事はそもそも始めてよいか|
|Pre-process|大漏れテスト|basis の不足や未解決の前提を検出する|権限 環境 タスク適合の不足を検出する|どこで早期停止すべきか|
|In-process|針のふれ監視|ドリフトが意味のあるものかを解釈する|進行 再試行 負荷 停滞を監視する|どこで監視の注意力を厚くすべきか|
|In-process|異常停止|仕事を hold に戻すべきかを決める|中断 縮退 引き継ぎを行う|継続がもはや admissible でなくなるのはいつか|
|Post-process|最終検査|比較が正当だったかを確認する|trace usage 実行履歴を提示する|何を受け入れ可能とみなしてよいか|
|Post-process|標準改訂|admissibility の条件を更新する|運用ループと safeguard を更新する|繰り返しの前に何を変えるべきか|

この表は単なる process map ではない。注意力をどこで厚くし、停止権限をどこに置き、あとで戻る可能性をどこに残すべきかを示す allocation map である。

## 5. 判定と実行は別のものを守っている

このように見ると、判定側と実行側の境界は理論上の細部ではない。実行側が守るのは flow であり、判定側が守るのは meaning である。前のエッセイはすでにこの区別を明示していた。実行順序を変えることと、comparability sufficiency completion を判断する基準を変えることは同じではない。前者が変えるのは flow であり、後者が変えるのは meaning である。この二つが混ざると、仕事は進み続けているように見えても、comparability は静かに崩れていく。

ここでの論点は、設計が、その境界を現実のものとして保つための希少資源を配分している、ということである。どこに停止権限を置くか、どこで preserved basis を必須にするか、受理の前にどれだけの review を要求するか、どこまでのコストを rerun の前に許容するか。そうした配分を決めることが設計の仕事である。

## 6. Partial Admissibility

verification resources は希少である。したがって、すべてを即座に全面 review することはできない。だから partial admissibility が重要になる。多くの仕事は、単純に accepted でも rejected でもない。見えてはいるが、まだ compare できない結果がある。有益ではあるが、まだ promote できない結果がある。いったん exclusion されるが、あとで judgment が戻ってこられるよう index だけは残すべきものがある。前のエッセイは、境界における操作上の区別として gate evidence contract を立てた。そこでは、gate はまだ admissible でないものを守り、evidence はまだ settled でないものを保存し、contract は何が正当な crossing と数えられるかを制限する。triage とは、それぞれをどれだけ、どこで、誰のコストで要求するかを決める配分である。

## 7. 偽の連続性

ここで、よくある failure mode が記述しやすくなる。ある process は、同じ inspection sheet の上を走っているように見えながら、その basis はすでに変わっていることがある。metrics は連続して見えるかもしれない。workflow はむしろ整理されたように見えるかもしれない。team は新しい状態を improvement と感じるかもしれない。しかし比較の basis が変わっているなら、その連続性の見かけは偽である。その仕事は、もはや意味のある仕方では同じ sheet の上を走ってはいない。

このような場合に失敗しているのは、単なる技術的規律だけではない。失敗しているのは triage である。false continuity は triage failure である。basis は変わったのに、停止権限は行使されなかった。replayability は強化されなかった。後で必要になる修復の負担は、見えないまま先送りされた。比較が一見きれいに見えても、それだけで correctness adoption legitimacy が保証されるわけではない。前提が変わったときに、連続性を黙って仮定してはならない。verification effort を再配分しなかったコストは、たいてい後で、しかも別の場所に現れる。

## 8. 標準改訂は責任の再配分である

だからこそ、standard revision はもっと鋭く理解されるべきである。改訂された標準とは、単に記述が改善されたものではない。それは admissible comparison の境界が改めて引き直されたということである。standard revision は、何を確認しなければならないか、どこで仕事を止めるべきか、何が comparable と数えられるためにどの条件が新たに必要になったかを再配分する。これこそが boiler code の深い教訓の一つだった。設計 製作 検査の規則は、ベストプラクティスを称揚するためだけに作られたのではない。反復する失敗が、ローカルな記憶や散在する熟練だけでは、規模のある安全を守れないことを示したからである。

## 9. AI は希少性を鋭くする

AI はこの問題を弱めるのではなく、むしろ鋭くする。前のエッセイは、agent design を擬人化された行為の神秘としてではなく、boundary design として読むべきだと論じた。agent は execution judgment gate handling evidence preservation contractual handoff のいくつかを束ねる。ここで付け加えるべき点は scarcity に関するものである。AI は throughput を、verification capacity が伸びる速度よりも速く押し上げる。review attention approval authority replay effort は、generation summarization automated execution と同じ速度では増えない。弱い premises は、もはやたまの局所的な誤りを生むだけではない。それは、修復コストがあとで別の場所に現れるような、速く分散した誤りを生む。次に問うべきなのは、何を automated できるかだけではなく、速度が上がるとき、どこで verification をより厚くしなければならないかである。

だから設計は、「何を自動化するか」を選ぶことだけに還元されてはならない。本当に難しい問いは、capability が上がるとき、どこで verification resources を厚くすべきかである。どの結果はなお view の水準に留めてよいのか。どの結果は compare の前に human review を必要とするのか。どの結果は formal adoption に進んでよいのか。どの結果は exclusion されても、あとで戻れるよう visible に index されていなければならないのか。こうした問いが設計の問いであるのは、それらが later judgment が shared basis の上でなお可能かどうかを決めるからである。

## 10. 三部作の到達点

この三部作は三つの段階を経てここに至る。第一のエッセイは、Structure Dynamics Observation View を与えることで explanation をより安定した座標へ戻した。第二のエッセイは、execution judgment gate evidence contract を与えることで、仕事が境界を越えても統治可能であるための操作語彙を立てた。そして本稿は、それらの区別が実務の中で機能し続けるための希少資源を、設計が一段上から配分していると論じた。

したがって、設計は単なる解の探索ではない。それは、あとからの judgment をなお可能にしておく条件を、規律をもって配分する仕事でもある。だから boiler code の歴史に見える教訓は、いまでも重要である。反復する失敗が要求したのは、より強い機械だけではなかった。要求されたのは、停止し、検査し、比較し、被害が拡大する前に改訂するための、より強い境界だった。

この教訓は、システムがより速く、より不透明で、より強力になるたびに戻ってくる。仕事は、より有能になったからといって、それだけで安全になるわけではない。設計が、何を進めてよいか、何を止めるべきか、何を provisional のまま残すべきか、何を visible に保っておくべきかを決めるときに、はじめて安全になる。そういう意味で、設計とは制約下のトリアージである。
