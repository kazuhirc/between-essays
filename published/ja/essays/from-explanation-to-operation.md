# 説明から操作へ

## 1. 仕事は説明だけでは進まない

5W1H は今でも有用です。何が起きたかを手短に説明する枠組みを与えてくれるからです。チームには要約が必要ですし、インシデントには記録が必要ですし、引き継ぎには共有された見取り図が必要です。その意味で、説明は仕事の一部であり、多くの場合かなり重要な一部です。

しかし、説明それ自体が仕事を前へ進めるわけではありません。結果はもっともらしく見えるかもしれない。変更には十分な理由があるように聞こえるかもしれない。誰が何を、なぜ変えたのかを、チームがきれいに語れるかもしれない。それでもなお、実務上の問いは未解決のまま残りえます。この結果は受け入れてよいのか、それとも保留すべきなのか。直前に受け入れられた状態と比較してよいのか。ここで止まるべきなのか、それとも次の境界を越えて進めてよいのか。

この隔たりが重要なのは、話が読めるようになった時点では、まだ仕事は完了していないからです。仕事が完了するのは、チームが比較可能性を保ち、前提が崩れたら止まり、判断を支える根拠を失わずに決定を境界の向こうへ運べるときです。ここで記述の語彙は力が足りなくなり始めます。何が起きたかは語れても、制約の下で行為をどう統御すべきかまでは、まだ語れません。

これがこのエッセイの出発点です。仕事は、説明だけでは表現しきれない、より豊かな構造の上で動いています。本稿の残りは、その構造に名前を与え、それが実行と判定の境界でなぜ重要になるのかを示します。

## 2. 仕事は小さな動きでできている

私たちはふつう、仕事を task や decision や deliverable の集まりとして語ります。これらの名前は便利ですが、多くの場合まだ粗すぎます。仕事が実際にうまくいくか、壊れるかが見える粒度では、そこにあるのは静的な項目の一覧ではありません。もっと小さな動きの連なりです。

何かが先へ渡される。何かが別の何かと比較可能なものとして扱われる。ずれが広がる前に、何かが止められる。あとで判断理由が読めるように、何かが残される。条件が明示されていることも、されていないこともあるまま、何かが境界を越えて受け渡される。これらは特別な操作ではありません。チームは日々、たいてい名前も付けないまま、こうした動きを使っています。

このように見ると、仕事には operational な肌理があります。仕事は、完成した成果物の列であるだけではありません。transfer、alignment、stop、preserved basis、handoff の列でもあります。説明はたいてい事後に来ます。動きが何を意味していたかを語るからです。しかし仕事は、その場で決めなければなりません。何が進んでよいのか。何が比較可能なのか。どこで止まるべきなのか。十分な basis があるのか。次の境界を安全に越えてよいのか。

こうした区別は、仕事が順調に流れているときには目立ちません。何かが早すぎる段階で前に送られたとき、止まるべきところで止まらなかったとき、十分な根拠がないまま境界を越えたとき、はじめてくっきり見えてきます。だから failure は、仕事の構造が最初に読めるようになる場所であることが多いのです。

## 3. その動きは failure のときに最もよく見える

こうした小さな動きは、失敗したときに最も見えやすくなります。仕事がうまくいっているとき、その構造の多くは暗黙のままです。結果は前へ進み、比較は自然に感じられ、止まるべきところで止まり、根拠は残り、handoff も十分うまくいくので、誰もその条件を改めて点検しません。流れが良いほど、構造は見えにくくなります。

failure が起きると状況は変わります。結果が早すぎる段階で前へ送られ、あとになってから、それが受け入れ済みの baseline と比較可能ではなかったと分かる。止まるべき地点を越えて処理が進み、修正のコストが外側へ広がっていく。reviewer には結果が見えているのに、それを承認すべき basis が復元できない。handoff 自体は行われたのに、受け取った側が、その前提となる promise が一度も明示されていなかったことに気づく。

そうした瞬間、仕事は急に読みやすくなります。問題は、もはや磨かれた narrative の背後に隠れていません。十分な条件がないまま何かが境界を越えたこと、安定した basis なしに何かが比較されたこと、適切な stop を経ないまま何かが継続したことが見えるようになります。failure が有益なのは、それが望ましいからではありません。成功時には黙ったまま通り過ぎる operational distinction を、failure が露出させるからです。

ここが本稿の議論にとって重要です。仕事の構造が failure によって見えるのだとすれば、次にやるべきことは、上から枠組みを持ち込むことではありません。failure がすでに露出させた区別に名前を与えることです。一見すると technical framework に見えるものも、実際には、実務者がすでに頼っていた区別を規律ある形で言い直しただけであることが多いのです。操作語彙は後から来ます。観察が先です。

## 4. 動きに名前を与えると、操作語彙が見えてくる

こうした小さな動きが見えたら、次の段階は、上から枠組みを押しつけることではなく、仕事の中にすでにあった区別に名前を与えることです。

execution は、仕事を前へ進めることです。次に何が走るのか、何が先へ渡されるのか、何が flow を通って継続するのかを扱います。judgment は、何かが次の段階へ進むのに十分比較可能か、十分か、十分に完了しているかを決めることです。gate は、必要な条件が満たされない限り、そこで止まらなければならない点です。evidence は、あとから判断を理解し、点検し、再演できるように残される basis です。contract は、gate と evidence が明示されたときに、境界越えを正当なものにする最小の operational promise です。

これらの語は形式的に見えるかもしれません。しかし、その区別自体はごく普通です。開発者はすでに、job を実行することと、その出力を受け入れることを区別しています。reviewer も、結果が見えていることと、承認に足る basis があることを区別しています。チームもまた、継続できる process と、止まらなければならない process を区別しています。この語彙が行うのは、新しい仕事を作ることではありません。control flow、comparison rule、stopping point、preserved basis、minimal promise を明示することです。

また、ここで初めて 5W1H との関係もはっきりします。Why 5W1H Breaks が扱っていたのは、説明を安定させるための記述上の座標系でした。本稿が始まるのはその先です。説明だけでは足りず、仕事を制約の下で統御可能に保つために、どんな語彙が必要になるのかを問います。

## 5. なぜ execution と judgment は分けなければならないのか 

ここが、executor と judge の境界へ向かう要点です。

execution の順序を変えることと、comparability、sufficiency、completion を判定する基準を変えることは、同じ変更ではありません。前者が変えるのは flow です。後者が変えるのは meaning です。両者は相互作用しますが、同じ操作ではありません。そして両者を同じものとして扱うと、仕事は脆くなります。

この脆さは実務では珍しくありません。pipeline を高速化するために簡略化したが、その過程で acceptance rule も明示されないまま緩んでしまう。workflow を扱いやすく書き換えたが、かつて出力を共通の baseline に乗せていた comparison rule が、静かに消えてしまう。見かけ上、process は健康なままです。仕事は前へ流れ続けるからです。しかし実際に壊れているのは flow ではなく comparability です。

だから boundary が要ります。execution は flow を司る。judgment は meaning を司る。gate はその境界を執行する。この役割が曖昧になると、仕事は前へ進み続けながら、comparability だけが静かに壊れていきます。

このように見ると、stop は官僚的な儀式ではありません。gate は後から付け足された ceremony ではありません。comparability を守るための保護です。前に進むための basis がまだ成立していないときに、仕事を先へ送らないようにする仕組みなのです。

## 6. 境界では、gate、evidence、contract が決定的になる

gate、evidence、contract の重要性が最もはっきり見えるのは、仕事が境界を越えるときです。結果が一つの段階を離れて次の段階へ入る。tool が reviewer へ handoff する。ある team が別の team に output を渡す。ローカルな decision が、別の誰かの input になる。そのとき問われるのは、単に仕事が完了したかどうかではありません。その crossing が正当かどうかです。

境界において legitimacy は三つのものに依存します。gate は、条件が満たされない限りどこで止まらなければならないかを定めます。evidence は、その crossing をあとで点検したり異議を唱えたりするための basis を保持します。contract は、受け取る側がその handoff を意味あるものとして扱うための最小の promise を明示します。この三つがなければ、crossing 自体は起こりえます。しかしそれは脆く、不透明な形で起こることになります。

## 7. AI agent は本当の謎ではない

この見方は、AI agent をめぐる現在の議論にも役立ちます。

AI agent はしばしば、それ自体が新しい種類の主体であるかのように語られます。しかし実務上は、その framing は見かけほど有用ではありません。agent はもっと素朴に、execution、judgment、gate handling、evidence preservation、contractual handoff のいくつかを束ねた operating unit として理解できます。

したがって本当に有益な問いは、神秘的な問いではありません。agent はどの操作を直接担うのか。どの judgment を許されるのか。どこで止まり、人間へ制御を返さなければならないのか。何を evidence として残さなければならないのか。その output を受け入れる前に、境界でどの minimal contract が成立していなければならないのか。

このように見ると、agent design は擬人的なラベルの問題ではなく、boundary design の問題になります。中心的な問いは、その agent が印象的かどうかではありません。その operational responsibilities が readable であり、controllable であり、reviewable であるかどうかです。

## 8. 説明から操作へ

5W1H が explanation の語彙の一部であるなら、execution、judgment、gate、evidence、contract は operation の語彙の一部です。

本稿が見えるようにしたい橋は、そこにあります。

言いたいのは、説明が不要になるということではありません。仕事には今でも narration が必要ですし、context も reportability も必要です。team は何が起きたか、なぜ起きたかを語らなければなりません。しかし、仕事を再実行し、確認し、止め、正当化し、境界の向こうへ移送しなければならなくなった時点で、説明だけでは足りません。必要になるのは、出来事だけでなく、その出来事を囲む control structure まで記述できる言葉です。

ここで between が役に立ちます。between は、仕事をもっと上品に語るための装飾的な語彙ではありません。comparability を守り、前提が崩れたときに止まり、evidence を保持し、仕事が境界を越える場所で最小の operational promise を明示するための、薄い語彙です。

だから between は抽象的な形式主義から始まりません。普通の仕事から始まります。decision を安全に境界の向こうへ送る前に、何を揃えなければならないのか。crossing のあとに何を見えるまま保たなければならないのか。あとで crossing が疑われたときに、何を回復可能にしておかなければならないのか。それを問います。その意味で between が主にしているのは、対象に名前を付けることではありません。守っているのは operational structure です。

これが explanation から operation への一歩です。そしてそれは、executor と judge の境界を、特殊な抽象概念としてではなく、実務上の区別として読めるようにする一歩でもあります。最初は technical vocabulary に見えるものも、実際には、実務者が毎日していることを規律ある形で言い直したものにすぎません。

用語は新しく見えるかもしれません。  
しかし、動きそのものは新しくありません。
