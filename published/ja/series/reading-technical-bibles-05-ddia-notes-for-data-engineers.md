# Reading Technical Bibles 05: DDIA — データエンジニアリングを「比較可能な観測」として読む

## 0. データは数値ではなく、観測である

データエンジニアリングは、数値を集める技術ではない。
観測を比較可能にするための技法である。
この失敗は、表計算でも、データウェアハウスでも、分散システムでも同じように現れる。結果だけが流通し、それを生んだ前提は消えてしまう。
Between は、この失敗を設計の問題として扱うための小さな語彙である。
このエッセイは、_Designing Data-Intensive Applications_（DDIA）を批判するものではない。ここで DDIA を取り上げるのは、「本番環境に多数の View が存在する」という状況を具体的に見せてくれるからであり、まさにその状況で比較可能性は設計課題になる。
DDIA には大幅に改訂された第 2 版があるが、そのことはむしろこの前提を強めるだけである。すなわち、本番システムは時間とともに、さらに多くの View を抱え込む。
本稿では、版ごとの章立てには依存せず、主題単位でこの本を読む。

一言で言えば、こうなる。
結果を比較可能なまま保つことは、データの問題ではなく、設計の問題である。

## 1. 比較測定において、差異はしばしば条件である

キッチンスケールには風袋引きボタンがある。
容器を載せてゼロにすると、表示は中身だけを語るようになる。
世界の何かが変わったわけではない。比較の基準面を固定しただけである。
この固定がなければ、見かけ上は比較できそうな二つの読みの中に、異なる隠れたオフセットが紛れ込み、その食い違いを対象の差、方法の差、前提の差のどれとして理解すべきか分からなくなる。
これが、「basis は検査可能でなければならない」ということの実践的な意味である。オフセットは計器の内側に隠された私的な事情ではなく、読み方の一部として見えていなければならない。
差異は、必ずしも誤りではない。条件の差かもしれない。
文脈が見えないままだと、そもそも比較できなかった数値について、あとから議論することになる。

## 2. 比較可能性とは何か――検査可能な Basis

比較可能性とは、「同じ指標を使った」ということではない。
「同じ footing の上で評価した」と、他者が確かめられることを指す。
basis が暗黙のままだったり、単一のスコアに押しつぶされていたりすると、外から見た人には、二つの結果が同じ前提を共有しているかどうかが分からない。
すると、性能差を対象の差、方法の差、basis の差に切り分けられなくなる。
目的は、集めたデータを退けることではない。比較が意味を失わず、食い違いが診断可能であり続けるように、basis を見える形で設計することである。

## 3. 本番環境における多くの View――DDIA を projection の本として読む

DDIA は、同じ現実に対する複数の projection をどう運用するかについての本として読むことができる。
データベース、インデックス、キャッシュ、ストリーム、マテリアライズドビュー、派生データセットは、いずれも View である。何かを保持し、何かを捨てる。
View が増えるにつれて、identity、時間、順序、欠測、再試行の振る舞いをめぐるズレは避けがたいものになる。
ここで本当に厄介なのは、「データが間違っている」ことではない。
「この結果が、どの前提のもとで生まれたのかを説明できない」ことである。
これは DDIA 自身の言い方ではなく、私の読みである。
次に問うべきなのは、こうしたズレがどこで生じ、比較可能性を保つために何を設計しなければならないのか、ということだ。

## 4. なぜ 3×3 マップが役に立つのか――比較可能性が壊れる場所を特定する

View が増えると、比較可能性がどこで壊れたのかを見つけにくくなる。
実際には、失敗は三つの段階に集まりやすい。Observe（取り込み）、Transform（導出）、Publish（利用・公開）である。
そして各段階で、三つのことを明示する必要がある。contract は境界で何を受け入れ、何を約束するか、basis は解釈が安定する footing、evidence は後から再検査するために何を残すか、である。
この二つの三項を掛け合わせると、「一致しない」という訴えを診断可能な位置へ落とし込める 3×3 マップが得られる。
それによって DDIA のトピックも、単なる技法の寄せ集めとしてではなく、特定のセルへの応答として読めるようになる。
シリーズ全体のグリッドでは、Basis は通常、Contract と Evidence の内側に埋め込まれている。だがここでは、あえて独立した行として立てる。データエンジニアリングの失敗は多くの場合、見えない footing――時間意味論、順序、identity key、そのほかの読みの条件――にまで遡るからであり、それらは「何が約束されたか」「何が記録されたか」とは別に診断する必要があるからである。

## 5. Contract――境界が比較を可能にする

多くの破綻は技術的な食い違いに見えるが、実際には境界をめぐる食い違いから始まる。
何を受け入れたのか。何を許したのか。何を約束したのか。
明示的な contract がないままデータが View のあいだを移動すると、解釈の違いは内部に埋もれ、最初の不一致は「本来は正しいはずだ」という議論になる。
contract は、境界における許容性と比較可能性を定義する。スキーマ期待、互換性ルール、エラー面、運用上の約束がそこに含まれる。
Evans の bounded context は、その具体例の一つである。
ただしここで言いたいのはもっと広い。比較を修辞ではなく安定したものにしたいなら、どの View 境界にも contract が必要だということである。

## 6. Basis――footing を固定し、見えるようにする

contract があっても、footing が見えなければ比較は失敗する。
basis とは、ある観測を解釈可能にする読みの条件である。時間意味論、順序、identity key、単位、丸め、再試行の振る舞いがこれに当たる。
こうしたものは実装の細部として片づけられがちだが、実際には比較そのものを支えている。
basis が暗黙のままだと、その差異が対象から来たのか、方法から来たのか、前提から来たのかを判別できない。
だから basis は、単一の出力値やダッシュボードの中に押し込めるのではなく、検査可能な形で外に出しておかなければならない。
同じ basis でも、パイプラインの各段階で現れ方は違う。
Observe では時間意味論とエンコーディング、つまりこのタイムスタンプが何を意味するのか、この文字列が何を指すのか、という問題になる。
Transform では順序と整合性になる。マージ、再試行、リプレイの際に、どの履歴を本物として扱うのかという問題である。
Publish では、利用者が目にする時間と鮮度になる。ウィンドウ、カットオフ、「最新」とはどこまで言ってよいのかが問題になる。
分散システムでは、read-your-writes や causal consistency のような整合性モデルも basis の一部である。
それらは、どの履歴やオフセットや並び替えを、読みに含めるのか、あるいは無視してよいのかを定めることで、何が比較可能な read なのかを固定する。
View ごとにその保証が違えば、「同じ指標」から計算された結果も、もはや同じ footing の上の観測ではなくなる。

## 7. Evidence――再検査できる連鎖を残す

何かが食い違ったとき、本当に問うべきなのは「誰が正しいか」ではない。
「何が起きたのかを、あとからもう一度たどれるか」である。
evidence とは、その再検査を可能にする最小限の記録である。入力、実行条件、依存関係のバージョン、適用した正規化、判断に使った閾値がそこに含まれる。
これは、やみくもにログを溜め込めという話ではない。
比較可能性に関係する事実だけを、差分として追える形で残そうという話である。
evidence があれば、食い違いは責任論ではなく診断へ変わり、診断は replay の入力へ変わる。

## 8. Sidecar――View を壊さずに前提を外に出す

ここでいう Sidecar は、Kubernetes の sidecar container pattern を指していない。
basis、contract、evidence を、主要な View を汚さずに外に持たせる、分離可能で差分可能な成果物を指している。

View は、説明のためではなく、使うために最適化されている。
そのため、basis や rationale を主要なデータセットや API payload の中に詰め込むと、多くの場合 View 本来の役割を壊してしまう。
sidecar は、basis、contract、evidence を、付属しているが分離可能な形で外に持たせる。追記可能で、構造化されていて、差分が取れる。
データシステムで言えば、schema registry、data contract、job metadata、quality rule、ADR、incident record はいずれも sidecar 的なものだと考えられる。
大事なのは、文書化そのものではない。
View を汚さずに、比較可能性を監査可能に保つことである。

## 9. 最小実装――Gauge を置く

contract は、「受け入れる」「拒否する」と言えるときに初めて現実のものになる。
その判断点が gate であり、そのための計器が gauge である。
感覚でパイプラインを止めることはできない。止めるなら、測定できる信号に基づいて止めなければならない。
gauge は正しさの証明ではない。
それは gate を正当化するのに十分な、安定した go/no-go 信号である。定理というより、パイロットランプに近い。

現場の比較測定が最終的に必要とするのは、ローカルな条件のもとで安定して OK と NG を分ける判断である。
だから工場では、管理された前提のもとで試験された既知の参照を使う go/no-go gauge が置かれ、「通るか、落ちるか」を安定して決められるようにしている。
データシステムであれば、本番スケジュール上で、本番環境のまま、「golden dataset + golden query」の組を定期的に走らせてドリフトを監視するのが一つの形になる。
そこに、実際の依存関係を踏ませる canary pipeline run と、互換性違反に対して即座に失敗する contract test を加える。

## 10. Replay――説明責任は再現可能性である

説明責任は主張ではない。
replayability である。
replayability とは、同じ basis と contract のもとで結果を再生成し、同じ gauge でもう一度判断できることだ。
ログやバックフィルや再処理に価値があるのは、それらが失敗回復と説明を可能にするからであって、正しさそのものを保証するからではない。
最小限の実践としては、参照入力である golden や canary を、バージョン、設定、時間意味論といった実行条件と束ね、変換をバージョン管理し、再処理の理由を sidecar に追記することである。
そうすれば、「結果が変わった」という事実は、「なぜ変わったのかを示せる」という状態へ変わる。

## 11. 結び――Excel から分散システムまで、同じ病理がある

Excel で壊れるものは、幼稚な問題ではない。
同じ病理が、より小さなスケールで現れているだけである。見えない footing、漂流するバージョン、蒸発する rationale、そして診断できない差分。
Between は、比較測定の直感を一般化し、View が増殖する状況でも比較可能性を保ち続けるための規律へと変える。
実際に始めるなら、まず gauge を置き、それを継続的に回すのがよい。
それが動き始めれば、missing basis、missing contracts、missing evidence は、抽象論ではなく、具体的なエンジニアリング課題として表面化する。
そのとき、この語彙は理論ではなく、設計を話し合うための共有言語になる。

## Postscript

このエピソードでは、ローカルな 3×3――Contract / Basis / Evidence × Observe / Transform / Publish――を使っている。
データエンジニアリングでは、パイプラインの段階が列軸として最も見通しがよいからである。
ただし、シリーズ全体の 3×3――Gate / Evidence / Contract × SSOT / Integration / Operation――は、なお共有座標として残っている。
このローカルな地図は、置き換えではなく、その内側に入れ子になった診断用の View である。

これをシリーズ全体のグリッドに戻して読むと、厚くしたセルは Gate × Operation、Evidence × Operation、Contract × SSOT である。
Gate × Operation は gauge に現れる。すなわち、ドリフトが広がる前に止める日常的な go/no-go 判断である。
Evidence × Operation は replay、lineage、reprocessing、そして何が起きたのかを他者が再検査できるようにする sidecar 的な連鎖に現れる。
Contract × SSOT は Observe の境界に現れる。つまり、何が比較可能な観測として入ってよいかを、許容条件とスキーマ期待が定める場所である。

Basis は、それらのセルを検査可能にしている内部内容である。
シリーズ全体のグリッドでは独立した軸ではなく、Observe、Transform、Publish を通って運ばれる宣言済みの footing として働いている。
ここで薄く残したのは Gate × Integration と Contract × Integration である。
それらはエッセイの端には見えているが、主たる重心は別の場所にある。境界の問題そのものは、bounded context へ向かう次の一歩に委ねている。

Transform 導出
contract: 変換仕様、互換性方針、品質要件

## Appendix B: 3×3 マップで DDIA を読む

各トピックを、単独の技法としてではなく、特定のセルへの応答として読む。
読むときは、次の二つの問いを立てる。

どこで比較可能性が壊れるのか。Observe、Transform、Publish のどこか。
何が欠けているのか。contract、basis、evidence のどれか。

短いメモでトピックをセルに対応づけていくとよい。
狙いは完璧な分類ではなく、「一致しない」を行動可能な形にすることである。

例をいくつか挙げる。

Replication lag → Transform × basis
レプリカが stale read を返すと、その暗黙の時間意味論は basis の一部になる。
それを名指さなければ、二つの「正しい」read は比較可能ではない。

Schema evolution Avro Protobuf → Observe × contract
取り込み時の互換性ルールは contract である。
それが明示されていなければ、旧スキーマと新スキーマのデータは、同じ観測であるかのように比較される。

Change Data Capture CDC → Publish × evidence
下流の View は、「どの上流状態」を反映しているかという evidence を必要とする。
それがなければ、replay や incident diagnosis は推測に落ちていく。

Consistency models Linearizability Serializability Eventual → Transform × basis
一貫性とは、どの履歴を本物として扱うかについての合意である。
ある View が linearizability を前提とし、別の View が eventual consistency しか前提としていないなら、それらは時間と順序について異なる basis の上で動いている。
その出力を直接比較すると、幻の不一致が生まれる。

Backwards compatibility of published interfaces API versioning schema-compat rules SLOs → Publish × contract
いったん View が他者に利用されるようになると、互換性は約束になる。何を変えてよいのか、エラーは何を意味するのか、レイテンシや鮮度をどこまで保証するのか、という約束である。
この contract がなければ、利用者は静かに解釈をずらし、不一致は「データのバグ」のように見えてしまう。本当は約束が壊れているのに、そのようには読めない。

Data freshness data SLA cutoff completeness → Publish × contract
「最新である」とは感覚ではない。contract である。
鮮度や cutoff のルールが暗黙のままだと、利用者は異なる publish 上の約束のもとで作られた値を、同じ footing を共有しているかのように比較してしまう。
