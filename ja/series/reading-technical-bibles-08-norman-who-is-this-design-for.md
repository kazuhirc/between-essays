**Reading Technical Bibles 08: Norman ― この設計は誰のためか**

**プロローグ**

設計とは何かと問うと、議論はすぐに抽象へ向かう。優雅さ、使いやすさ、性能、堅牢性。どれも間違ってはいない。だが、それだけでは、いま多くのエンジニアが実務で感じている圧力を十分には捉えきれない。律速は、もはや以前と同じ場所にはない。長いあいだ、ソフトウェアの仕事は主として実装に制約されているように見えていた。誰がコードを書けるのか、どれだけ速く作れるのか、構想から成果物へどこまで細部を運べるのか。ところが、LLMが実装のコストを下げるにつれて、圧力は別の場所へ移っていく。いま重要なのは、何が書けるかだけではない。何が読めるか、何が信頼できるか、そしてシステムのどこで先へ進み、どこで止まるべきかである。

その意味で、ここでNormanを読む意義がある。対象そのものとしてではなく、ひとつのレンズとしてである。彼の語彙、すなわち signifier、feedback、conceptual model、constraint は、設計とは単に機能を成立させることではなく、次の一手を読める形にすることでもあると気づかせてくれる。こう読めば、これらは単なる usability の原則ではない。境界をどう設計するかを考えるための手がかりである。何を見せ、何を隠し、どこで解釈を行為に足るほど安定させるのかを考えるための手がかりである。

このエッセイが問うのは、もう少し絞られた問いである。読者を end user の外へ広げたとき、この設計は誰のためのものなのか。こう読み替えると、Normanは usability の理論にとどまらず、judgment surface を考えるためのレンズになる。システムが何を可視化し、何を内部に留め、どこで異なる読者が先へ進めるのか、あるいは止められるのかを考えるためのレンズになる。

**Section 1 ― ボトルネックはどこへ移ったか**

長いあいだ、ソフトウェアの仕事で目に見える制約は実装だった。誰がコードを書けるのか、どれだけ速く作れるのか、どれだけ確実に構想を成果物へ変えられるのか。書く技能が見かけ上の律速であり、設計の語彙の多くもその制約の周囲で育ってきた。抽象化、モジュール性、命名、結合、性能。どれも重要である。だが、システムの最も狭い場所は移りつつある。

いまやLLMは、数年前なら過剰にすら思えた速度と量で実装を生み出す。リファクタリング、ラッパー、テスト、果てはモジュール一式まで、数分で現れる。書くコストは下がった。しかし読むコストは、それに合わせて下がってはいない。むしろ、読むことは以前より難しくなった。レビューし、検証し、受け入れるか退けるかを判断しなければならない出力の量が増えた一方で、人間の判断能力そのものは増えていないからである。

つまり、ボトルネックは実装から review、verification、consent へ移っている。より難しい問いは、ますます「これは書けるか」ではなく、「これは読めるか」「どこで止まるべきか」「何をもって正しいという証拠とするか」「それを進めてよいと判断する責任を誰が持つのか」になっている。これらは設計の問いである。しかしそれは、成果物の後ではなく、その手前、しかも読むという行為により近いところで現れる。

**Section 2 ― コードが成果物になる前に設計は起きている**

コードはいまも、ソフトウェア仕事の中心的な成果物のように見える。だが、もっとも帰結の大きい設計判断の多くは、コードが注意の中心になる前に下され、しかもコードが書かれたあとにも長く効き続ける。コードが成果物になる前に、設計はまず、何を readable surface とみなすかを決める。何を interface として露出するか。何をその背後に隠すか。どの状態を観測可能にするか。どのログを evidence とみなすか。どの error message が次の人に問題の位置を教えられるか。どの view が user 向けで、どれが operator 向けで、どれが reviewer 向けで、どれが future maintainer 向けなのか。

これらはすべて reading surface である。interface は reading surface である。error message もそうである。code review の diff も、dashboard も、log stream も、permission prompt もそうである。これらは「本当の設計」が終わったあとに付け足される二次的な装飾ではない。設計そのものの一部である。なぜなら、何が見えるか、どこで行為を止められるか、何があとで正当化として数えられるかを決めるからである。

この区別は重要である。設計が責任を持つ範囲そのものを組み替えるからだ。もし設計が単にプログラムを動かすことだけを意味するなら、成果物が終点になる。だが、設計が異なる役割を持つ異なる人々にとって、プログラムを readable で operable なものにすることも含むなら、reading surface は設計への付属物ではない。それは judgment に接続する設計の第一の interface である。コードは見えている結果にすぎない。設計とは、judgment がどのように配分されるかについての事前の決定である。

**Section 3 ― Normanを judgment surface のレンズとして読む**

ここでいう judgment surface とは、読者に、次に何ができるか、何を確認しなければならないか、何を結果として数えるかを知らせるシステムの部分である。ここでの関心は、Norman の語彙を一つずつ解説することではない。judgment surface がどのように設計されるかを問うために、彼の概念を道具として使うことである。

Norman のいう signifier とは、ある行為が可能だと知らせるものである。引いて開ける形のドアハンドルは「ここを引く」と知らせる。平らなプレートは「押す」と知らせる。signifier が間違っていると、たとえば押すべきドアに引き手が付いていると、読者は状況を誤読し、誤った行為をしてしまう。これはNormanでもっともよく知られた観察だが、そのまま移し替えることができる。Between の語彙で言えば、signifier とは gate に置かれた judgment surface である。それは読者に次の妥当な行為が何かを知らせる。そして signifier が欠けているか、誤解を招くとき、読者は正しいタイミングで止まれない。誤ったハンドルのドアとは、機能し損ねた gate である。読者に技能が足りないからではなく、次の判断に必要な情報を surface が運んでいないから、誤って通過してしまうのである。

feedback とは、行為の結果を観測可能にするものである。カチッと音はするのに、離れた部屋で何も変化が見えないライトスイッチは、行為者を不確かなままに置く。Norman はこれを設計の失敗とみなす。システムは動いたが、その結果が、それを必要とする人へ返ってこないからである。Between の語彙で言えば、feedback とは、次の judgment が必要とする速度で返される evidence である。CI パイプラインが走っても、理由を読める形で返さず、単に pass か fail だけを返すなら、それは evidence を伴わない feedback である。行為は完了したが、reading surface が次の判断を支えていない。どんな応答でも feedback になるわけではない。次の judgment を支えられるほど速く、かつ明瞭に返るときにだけ、それは feedback になる。

conceptual model とは、システムがどう動くかについての期待である。user の model と designer の model が一致していれば、システムは予測可能に感じられる。ずれていれば、user は正しい挙動に驚くか、もっと悪い場合には、誤った挙動に驚かなくなる。Between の語彙で言えば、これは境界をまたぐ shared contract である。期待がそろうことで境界が保たれる。contract は、明示的で形式的である必要はない。読者の予測とシステムの挙動が、気づかれないまま乖離しない程度には安定していなければならない。

このように読むと、signifier、feedback、conceptual model は、ばらばらの三原理ではない。ひとつの設計問題の三つの相である。すなわち、次の人が行為し、止まり、検証できるだけの可読性を境界にどう与えるか、という問題である。

**Section 4 ― 隠すことは注意を守ることである**

Norman の四つ目の概念、constraint は、誤った行為を構造的に不可能にすることに関わる。一方向にしか刺さらないUSBプラグは constraint である。必須項目が埋まるまで送信ボタンがグレーアウトされたフォームも constraint である。目的は user を縛ることではない。システムが回復できない状態や、user が診断できない状態へ至る遷移を閉じることである。

ここで「隠す」という動詞が面白くなる。ソフトウェア設計では、hiding はしばしば秘密のように語られる。implementation detail を隠して、外部コードがそれに依存しないようにするためだ、と。Ep04 では information hiding を change propagation の封じ込めとして読んだ。Norman は同じ動詞を、attention の保護へ向け直す。境界そのものは残り、受益者が変わる。隠されるのは秘密だからではない。それを露出すると、読者が本当に重要なことへ行為するための注意容量が過負荷になるからである。

両者に共通する構造的な主張は、境界は「通さないもの」によって設計されるという点である。Between の語彙で言えば、どちらも gate design である。すなわち、何が境界を越え、何が越えないかを決めることだ。違うのは、その gate が封じ込めようとしているコストである。change propagation のコストなのか、attention のコストなのか。

つまり、hiding は設計の不在ではない。もっとも意図的な設計行為の一つである。あらゆる interface、あらゆる abstraction、ある指標を落とした dashboard、ある event を落とした log level、その一つ一つが、誰の注意を守り、どのコストを支払うかについての決定である。うまく決められていれば、読者は必要なものを見て、不必要なものに気を散らされない。まずく決められていれば、読者は無関係な詳細に溺れるか、本来 stop を促すべき信号を見落とす。

**Section 5 ― この設計は誰のためか**

Norman が主に書いたのは end user についてである。ドアを開ける人、サーモスタットを調整する人、コンロを扱う人。designer が自分自身や技術の都合で作りがちで、実際にそれを使う人のために作っていない、というのが彼の中心的な関心だった。この関心はいまも妥当である。だが、ソフトウェアシステムでは、end user は設計が支えなければならない読者の一人にすぎない。

reviewer は diff、pull request の説明、test result を読む。彼らの judgment surface は動いているアプリケーションではなく、変更そのものである。何が変わったのか、なぜ変わったのか、その変更を merge して安全かどうか。operator は dashboard、alert、log stream を読む。彼らの judgment surface はシステムの現在状態である。何が動いているのか、何が変わったのか、何が閾値に近づいているのか。maintainer は dependency graph、module boundary、documentation を読む。彼らの judgment surface はシステムの構造である。何が安全に変更できるのか、何が結合しているのか、どこへ変更が波及するのか。future maintainer、すなわち自分が作っていないシステムを保守しなければならない人は、これらすべてを読むことになる。しかも、元の判断を可読にしていた文脈を持たないまま読むことが多い。

これらの読者は、それぞれ異なる judgment surface を必要とする。user を助ける signifier 「ここをクリックして進む」は、reviewer を助ける signifier 「この diff は認証境界を変えている」とは違う。operator を助ける feedback 「応答時間が閾値を超えた」は、maintainer を助ける feedback 「このモジュールは過去1四半期で4チームに変更された」とは違う。user を助ける conceptual model 「このアプリは自動保存する」は、future maintainer を助ける conceptual model 「このシステムは単一リージョン配置を前提としている」とは違う。

Norman の問い、この設計は誰のためか、には単一の答えはない。設計の質は、system が end user にどれだけよく仕えるかだけでは決まらない。行為し、止め、検証し、次へ手渡さなければならない複数の読者へ、どれだけ readable な judgment surface を適切に配分できているかでも決まる。

**Section 6 ― 設計とは judgment、負担、責任の配分である**

もし設計を judgment surface の配分として読むなら、その質は成果物が動くかどうかだけでは決まらない。適切な人が、適切なものを、適切なタイミングで見られるか。危険なステップを、波及する前に止められるか。そこに設計の質が現れる。

すると設計は allocation problem として見えてくる。配分されているものは三つある。第一に judgment である。何を、誰が、どんな evidence に基づいて判断しなければならないのか。よく設計されたシステムは judgment を消さない。十分な情報のもとで行使できる場所へ judgment を置く。第二に burden である。何を読まなければならないのか、どれだけを注意の中に保持しなければならないのか、何がフィルタで落とされるのか。よく設計されたシステムは burden をゼロにしない。各読者が自分の役割に関係するものだけを負うように burden を配分する。第三に responsibility である。何かが止められなかったとき何が起こるのか、誰が accountable なのか、そして retrospective のためにどんな evidence が残るのか。よく設計されたシステムは blame を割り当てない。判断の経路を回復可能にする。

Norman は、たとえドアであっても、読者に次に何をすべきかを伝えられないなら、設計として失敗しうることを示した。同じ論理はそのままスケールする。正しく動いていても、review できず、安全に止められず、次の maintainer に理解できず、failure のあとに inspection できないソフトウェアシステムは、内部がどれほど elegant でも、よく設計されているとは言えない。成果物が動いた時点で設計は終わらない。境界が引かれたときに終わる。誰が何を見るのか、誰が何を止めるのか、次に誰が何を保つのか、そして judgment が下された証拠として何が残るのか。その境界が引かれたときに、設計はようやく完了する。

重要なのは、システムが生み出す成果物だけではなく、それを readable かつ operable にする境界である。成果物とは、それらの境界が引かれたあとに残るものである。

**追記**

3×3 のレンズで見ると、この回が主に厚くしたセルは三つである。

この回で厚くしたセル

- Gate × Operation  
    signifier と constraint を、日常的な相互作用の中に設計された stop として読む。読者が何を見るかが、どこで止まれるか、どの遷移が閉じられるかを決める。
    
- Evidence × Operation  
    feedback を、次の judgment が必要とする速度で返される観測可能な帰結として読む。evidence とは記録管理ではなく、次の判断を可能にするものである。
    
- Contract × Integration  
    conceptual model を、境界をまたぐ shared expectation として読む。model が気づかれないまま乖離すると、境界はもはやその約束を運ばない。
    

意図的に薄く残したセル

- Evidence × SSOT  
    master reference がなぜそのように定義され、あるいは改訂されたのか。このセルは将来の回へ残してある。
    
- Gate × SSOT  
    master 自体をいつ凍結し、いつ問い直すべきか。Norman はこれを直接は扱わない。別種の圧力に属する。
    
- Contract × Operation  
    日常的に用語を共有し更新する手続き。Norman の語彙は単一 user を前提としている。Section 5 の multi reader への拡張はこのセルを指し示すが、まだ厚くはしていない。
    

**読み直しキット**

Norman を読むときは、ひとつの operational な問いを持ち込むとよい。この surface の読者は誰か。そしてその読者は、次に何ができなければならないのか。

Norman が設計失敗を描写するたびに、たとえば分かりにくいドア、読みにくいコンロ、不透明なリモコンを描写するたびに、その失敗を三段で書き換える。第一に judgment surface を特定する。読者は何を見るはずだったのか。第二に missing gate を特定する。読者はどこで止まるか、あるいは選ぶことができるべきだったのか。第三に missing evidence を特定する。どんな feedback があれば次の判断が可能になったのか。

そして読者を拡張する。Norman は end user について書いている。同じ三つの問いを reviewer、operator、maintainer、future maintainer にも向けてみる。失敗の形は変わる。しかし、その構造、surface、gate、evidence は変わらない。
