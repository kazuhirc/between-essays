
# "What Appears When Execution Gets Cheap" 実行が安くなったとき、足りなくなるもの


## 0. 導入

ものづくりでは、測定値そのものより先に、何を基準に、どの条件で、どの向きから比べているかが重要になります。同じ品物でも、基準面が違えば値は変わります。同じ数字が並んでいても、測り方が違えば、その二つをそのまま比べることはできません。違いが出たときにまず問うべきなのは、どちらが正しいかだけではなく、この二つは本当に同じ土台の上にあるのか、ということです。

この感覚は、加工でも同じです。ものづくりの世界では、数値制御の発明と普及によって、加工の実行能力が大きく上がりました。速く、正確に、同じ手順を繰り返せるようになった。そのこと自体は大きな前進でしたが、同時に別のことも前景化しました。基準が揃わないまま実行が走ると、不良は一つずつではなく、まとめて、しかも正確に出るということです。原点、治具、座標系、工具長補正、段取り条件がずれたままなら、実行能力の高さはそのまま不一致の増幅装置になります。

いま AI のまわりで起きていることも、かなり近い形をしています。実行のコストが下がり、出力は先に増える。けれども、何を同じものとして読むか、どこで止まるか、何を残して同じ判断へ戻るかといった条件は、自動では揃いません。むしろ実行が安くなるほど、その不足の方が先に目立ちます。手で一つずつ進めていたときには見えにくかったずれが、速く大量に流れることで、かえってはっきり見えるようになるのです。

いま不足として見え始めているのは、実装や生成の能力そのものではなく、その外側で判断を支える層です。私はこの文章で、その不足がどこで見え、なぜ今はっきりしてきたのかを考えたいと思います。

## 1. 現場の起点

機械設計の現場では、ひとつの文書だけを見て仕事が完結することはほとんどありません。図面があり、BOM があり、仕様書があり、検査指示書があります。それぞれにはそれぞれの正しさがあります。図面は形状を正しく表しているかもしれない。BOM は部品構成を正しく持っているかもしれない。仕様書は要求を正しく書いているかもしれない。検査指示書は受け入れ条件を正しく示しているかもしれない。けれども、次の判断に進もうとした瞬間に、どこかで手が止まることがあります。

この止まり方は、単純な誤記や入力漏れとは少し違います。たとえば、形は変わっていないのに測定方法だけが変わっている。部品番号は合っているのに、置換理由や適用時期がずれている。図面も表もそれぞれ単独では整って見えるのに、実際の作業に引き継ごうとすると、同じ対象を見ている感じが急に薄くなる。ひとつひとつの文書の中では破綻していないのに、文書のあいだを渡ろうとしたところで判断がこぼれます。

ここで起きていることは、どれか一枚の文書の失敗だけではありません。壊れているのは、二つの読み、二つの出力、二つの判断を、同じ土台の上に置いて比べられる条件です。図面、BOM、仕様書、検査指示書は、それぞれ局所的には正しくありうる。それでも、そのあいだで同じ判断が保てなくなる。問題は情報が足りないことだけではなく、同じものとして並べるための足場が失われることにあります。

そして、この壊れ方には順番があります。まず、同じ土台の上に置けなければ、どこで止まるべきかを決められません。次に、止まれなければ、なぜ止まったのかという理由や証跡が局所化されません。さらに、証跡が局所化されなければ、あとから同じ判断へ戻ることができません。比較、停止、再開は、並んだ機能ではなく連鎖です。現場で起きているのは、単なる文書管理の不備ではなく、この連鎖が途中で切れてしまうことです。ここで壊れているものに名前を与えるなら、比較可能性がいちばん近いと思います。
## 2. なぜ今これが見えたか

この問題そのものは、新しくありません。比較が崩れると止まれず、止まれないと証跡が残らず、証跡が残らなければ同じ判断へ戻れない。そうした不具合は、昔からありました。けれども、しばらくのあいだは実装の重さがそれを覆っていました。そもそも作ること自体が大変だったので、判断の条件が十分に整っていないことは、作る苦労の陰に隠れやすかったのです。

いまは事情が少し違います。生成のコストが下がり、出力は先に増えます。コードでも文書でも図でも、形になるものは以前より速く出てきます。けれども、レビューする人の注意力、承認する人の時間、あとから同じ判断に戻るための証跡は、同じ速度では増えません。ここに非対称があります。実行の能力は先に伸びるのに、検証と承認の能力はそれに合わせて自動では増えないのです。

その結果、圧力は実装そのものの内側ではなく、外側へずれてきます。何を根拠に受け入れるのか。どこで保留するのか。何を痕跡として残すのか。どこまでを自動で進め、どこから人に返すのか。最近よく見かける memory や review loop や permission や trace の議論は、流行の飾りではありません。生の生成能力だけでは支えきれない部分を、外側からなんとか補おうとしている局所的な工夫です。

言い換えると、いま前景化しているのは、賢い生成器をどう作るかだけではありません。生成されたものを、同じものとして読み、必要なところで止め、あとから同じ判断へ戻れるようにするには、外側にどんな設計が必要か、という問いです。そして、その設計が何を守ろうとしているのかを言い表す語彙は、まだ十分には揃っていません。

## 3. Between は何を支えるか

Between は、その不在に対するひとつの応答です。judge の別名でもなければ、単独の protocol でもありません。まして、あらゆる分野を一つの形式で包み込む完成済みの標準でもありません。ここで言いたいのはもっと薄い層です。比較が成立する条件を支え、必要なところで停止を正当化し、その停止理由をあとから辿れるようにする中間層。Between は、まずそのようなものとして考えた方がよいと思います。

この層が支えるものは、三つにまとめて言えます。第一に、比較のための足場です。何を基準に比べるのか、その比較がどんな条件のもとで有効なのか。第二に、停止のための境界です。条件が崩れたときにどこで止まり、なぜ止まったのかをあとから見直せるようにする。第三に、再開のための痕跡です。いったん止まったあとで、どの判断点からやり直せばよいのかを失わないようにする。比べるための足場、止まるための境界、戻るための痕跡。この三つが揃って、はじめて判断が個人の記憶から少し離れて共有可能になります。

もう少し細かく言えば、比較のためには参照面と比較条件が必要です。停止のためには停止点と証跡が必要です。再開のためには戻り先の経路が必要です。Between が支えたいのは、正解そのものではありません。何が正しい図面か、どの公差が妥当か、どの設計判断を採るべきかは、依然として各ドメイン側に残ります。Between が支えるのは、その判断を比較可能にし、停止可能にし、再開可能にするための条件です。だからこれは、意味内容そのものというより、意味が崩れずに運ばれるための中間層だと言った方が近いです。

既存の比喩で近いものはいくつもあります。治具は位置を安定させますし、負帰還は逸脱を抑えますし、トレースの仕組みは伝播経路を残します。けれども、それぞれが照らすのは一面だけです。Between が扱いたいのは、位置決めだけでも、制御だけでも、記録だけでもありません。比較、停止、再開がひと続きの連鎖として成立する条件の束です。だから一つの比喩では少し足りません。

## 4. おわりに

ここまで見てきたものは、完成した標準ではありません。まだ用語は揺れていますし、実装の形も分野ごとにばらついています。あるところでは gate として現れ、あるところでは sidecar のような付属物として現れ、別のところでは評価条件や trace のような形で現れます。ひとつの完成品がすでに手元にある、という話ではありません。

けれども、それを曖昧だと言って済ませるのも違うと思います。骨格はもう見えています。比較が壊れる前に止める仕組み。止まった理由をあとから辿れる痕跡。戻るべき判断点を失わないための参照面。そうしたものは、名前の揃わないまま、いくつもの現場で部分的に働いています。いま必要なのは、何もないところから壮大な仕組みを発明することではなく、すでに働いている条件の束を取り出して、比べられる形に整えることです。

その意味で Between は、未来の完成品の名前というより、すでに断片として存在している骨格を読むための名前です。生成が速くなるほど、実装そのものより、その外側で判断を支える条件の方が不足として目立ってきます。だから問うべきことも、以前とは少し変わります。何を同じものとして読むか。どこで止まるか。何を残して同じ判断へ戻るか。いま見え始めているのは、その三つを個人の勘や記憶ではなく、共有可能な条件として支える層です。

この層は、まだ十分には言語化されていません。けれども、見えていないわけでもありません。だから次に必要なのは、賢い生成器をさらに増やすことだけではなく、その出力が判断を壊さずに流れるための骨格を、少しずつ取り出していくことだと思います。
