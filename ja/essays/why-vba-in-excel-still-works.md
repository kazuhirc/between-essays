# なぜ Excel 上の VBA は今も生きているのか — そして Excel 上の AI が守るべきもの

*どんな近代化の波をくぐっても残る、運用上の性質について*

---

## 置き換えられなかったマクロ

数年おきに、それを置き換えようという話が持ち上がる。

ワークブックは古い。VBA はもつれている。名前付き範囲には、一人しか意味を知らない名前が付いている。コンサルタントは REST エンドポイントとちゃんとしたデータベースを備えた、きれいなアーキテクチャ図を描き、皆がうなずく。
ところがその後、プロジェクトは止まる。あるいは、ケースの 70% しかカバーできないままリリースされ、古いワークブックが静かに現場へ戻ってくる。

私はこの循環を、これまでの仕事の中で三度見てきた。置き換え案は毎回、技術的には優れていた。それでも毎回、元の仕組みが生き残った。人々が頑固だったからではない。置き換え案が、その表計算が実際に果たしていた役割を果たせなかったからである。すなわち、意思決定を前に進めながら、あとで別の誰かが確認できるだけの文脈を保つ、という役割である。

このエッセイは VBA を擁護するものではない。
ここでやりたいのは、設計、製造、購買、検査が交差する運用の最前線で、なぜ Excel 上の VBA が思いのほかしぶとく機能してきたのか、その性質に名前を与えること。そして、もし Excel 上の AI が同じ場所を担いたいなら、何を守らなければならないかを考えることである。

---

## 1. 成果物は表計算ではない。意思決定の連鎖である。

多くの組織では、表計算そのものが成果物だとみなされている。
しかし本当に重要なのは成果物そのものではない。そこに表れている意思決定の連鎖である。

現場の典型的なワークフローは、「入力して、計算して、出力する」というより、次の流れに近い。

1. 何かを読む。客先図面、過去案件、仕様書。
2. 候補を導く。計算を回す、マクロを呼ぶ、あるいは今なら AI に尋ねる。
3. 比較して判断する。差分を見て、制約を確かめ、参照先を当たる。
4. commit する。図面を発行する、発注を送る、検査結果を登録する、マスタを更新する。

commit の前では、作業はまだ戻せる。
commit の後では、修正は調整、手戻り、説明に変わる。
実際の仕事では、一つの案件の中に複数の commit があることが多い。そして commit のたびに、新しい不可逆な境界が生まれる。運用コストが集中するのは、まさにその境界である。
そして、その境界においてこそ、Excel 上の VBA は驚くほど頼れるものとして機能してきた。

この連鎖の出力は、単なる数値ではない。
あとから別の誰かが、別の道具を使っても再確認でき、それでも同じ判断として受け入れられる、防御可能な決定である。

## 2. 設計者が尊重すべき四つの性質

VBA は古く見えるので、軽く扱うのは簡単である。
しかし問題は古さではない。
よりきれいな設計が機能しない場所で、なぜそれが動き続けるのかである。
その答えは、言語仕様ではなく、アーキテクチャ上の四つの性質にある。

### データへの近さ

VBA は、運用上の真実がすでに存在している場所で動く。
マクロは、オペレータがいま見ているそのシートを読み、同じ概念の枠の中でデータを変換し、その結果を同じ成果物へ書き戻す。
文脈を剥ぎ取ってしまうシリアライズ層はそこにない。
ロジックをシートの外へ出した瞬間、抽出、写像、検証、同期といった境界が生まれる。そして境界が増えるたびに、新しい失敗モードと新しい人間の作業が増える。

### 配布の単純さ

マクロ付きワークブックは、コピーでき、共有でき、管理者権限がなく、依存が一つ増えるだけでも政治的負担になるような環境で動かせる。
現場の自動化が失敗する理由は、アルゴリズムの複雑さであることはむしろ少ない。失敗するのは、配布、保守、ドリフトにおいてである。
単一成果物として配れることは、それらのコストを十分低く保つので、組織は段階的な改善を受け入れられる。
置き換えを提案するなら、実行速度だけでなく、この運用上の優位を上回らなければならない。

### Human-in-the-loop が既定であること

多くのマクロは、端から端まで一気に流れる自動パイプラインではない。
入力を確認し、選択を確かめ、出力を見直し、書き戻す前に承認する。そうした意図的な停止点を持つ段階的な手順である。
この仕組みによって、状態を失わずに stop-and-recover ができる。
これは制約ではない。
曖昧さ、不完全な要件、そして熟練者にしか解釈できない制約を前提とした設計である。

### 暗黙の契約

多くの VBA ワークブックは、明文化されていない前提に依存している。名前付き範囲が存在すること、列に特定の意味があること、参照表が最新であること、実行前に特定のセルが埋まっていること。
こうした前提は文書化されていないことが多いが、コードの中で「確認して止める」ことで実質的に強制されている。
つまり、多くのマクロは計算機であると同時に、validator や gatekeeper としても働いている。
「先へ進む前に何が真でなければならないか」をコード化し、オペレータ間や時間をまたいだばらつきを抑えているのである。

この四つは VBA の機能ではない。
運用上の不変条件である。
これを捨てる置き換えは、技術的には優れていても、運用面では脆くなる。

## 3. AI は失敗モードを変える

従来の Excel のリスクはよく知られている。
式の誤り、参照先の誤り、静かなコピーミス。
これらは correctness の失敗であり、痛みはあっても診断可能である。式は見える。セルは追える。マクロはステップ実行できる。成果物の中には、その結果がどう得られたかについて、ある程度の説明が残っている。

ところが Excel に埋め込まれた AI は、支配的な失敗の形を変える。
問題はもはや、「シートが間違った値を計算した」ではない。
「その値が、なぜ受け入れてよいのかをシートが説明できない」になる。

これは仮説ではなく、かなり具体的である。

* 同じプロンプトでも、日によって違う答えが返る。モデルの非決定性と静かな更新によって、出力は動く標的になる。
* 入力文脈と道具の同一性が残らない。ソース、前提、参照表、場合によってはモデル版さえ欠けるので、ドリフトを境界づけることも説明することもできない。
* オペレータが結果を commit しても、あとから何を読み、どの条件のもとで、どの権限に基づいてそうしたのかを再構成できない。

その下流で起こることは予測しやすい。
provenance が弱いと、組織は人手で埋め合わせる。レビューが増え、会議が増え、差し戻しが増え、承認が増え、最終的には遅延が増える。
シートは速く見える。ワークフローは遅くなる。

問題の核心は知能ではない。
comparability である。
つまり、「同じ宣言済み条件のもとでは、この結果とあの結果は、たとえ道具や担当者が変わっても同等とみなしてよい」と言える能力である。

業界の動きも、この問題が現実であることを示している。
一部のクラウド分析製品はすでに、データソース、指示、検証済みの定義をまとめて梱包し、対話型ワークフローを安定させようとしている。
ただし、そうした解決策は多くの場合、そのプラットフォーム内に閉じている。
ここで述べるアプローチは、異なる道具をまたいで止まり、回復できるようにするための、持ち運び可能な規律——明示的な gate、確認可能な成果物、順序づけられた evidence——に焦点を当てている。

## 4. パターンを示す失敗例

具体例を通すと、論点はよりはっきりする。
以下はいずれも単発の事故ではなく、実際に繰り返し現れるパターンである。

### テンプレートのドリフト
あるチームが過去のワークブックをテンプレートとして使い回す。中の参照表は古いが、出力はそれらしく見えるので誰も気づかない。二週間後、別のオペレータが lookup table を一つだけ更新して同じファイルを走らせると、出力が食い違う。どちらも「もっともらしい」。どちらが受け入れてよいのかを説明できる人はいない。結果は会議と、静かな書き直しである。

これは計算ミスではない。
足りなかったのは前提条件である。参照表の版が宣言も確認もされていなかった。

### provenance のない AI 要約が出荷される
Excel 上の AI が客先図面の要約を生成し、パラメータ値を提案する。オペレータはそれをシートへコピーする。あとでエンジニアが、なぜその公差が選ばれたのかを尋ねる。プロンプトは保存されておらず、入力図面へのリンクもなく、モデル版も不明である。残っているのは最終値だけである。

これは主として「AI の hallucination」の問題ではない。
provenance の失敗である。
その意思決定を防御可能にする参照が付かないまま commit されてしまったのである。

### 同じ品番、異なる条件
二人のオペレータが、同じ部品に対して同じ検査指示書を生成する。一人は水平取り付けを前提とし、もう一人は垂直取り付けを前提とする。文書はどちらも内部的には正しく見える。検査段階になって初めて、測定軸が違い、結果が比較可能ではないことに気づく。

どちらの文書も「間違っている」わけではない。
取り付け条件が意思決定に結び付けられていなかったのである。

### 外部依存が静かに変わった
あるワークブックが共有ドライブ上の lookup table を使っている。パスは変わらないが、中身だけが更新される。先月作った案件を、今日は再現できない。チームはドリフトを見て「誰かがミスした」と考えるが、本当の原因は依存のドリフトである。

### 承認が前提扱いされていた
若手エンジニアが、マクロが許していたのでマスタシートを更新する。一週間後、先輩エンジニアがなぜマスタが変わったのかを尋ねる。若手は「ツールができたからです」と言い、先輩は「それを commit していいことにはなっていない」と言う。組織は手動ルールを一つ追加する。ツールそのものは変わらない。

どのケースでも、失敗は計算の中にあるのではない。
境界にある。
意思決定と一緒に運ばれるべきものが、それから切り離されてしまったのである。

## 5. 一緒に運ばれなければならない五つのもの

私はこの最小の意味論レイヤを Between と呼ぶ。
それは、道具や時間をまたいで意思決定を比較可能に保つためのやり方である。
これらの失敗に共通するパターンは一貫している。
意思決定は、それを支える参照から切り離されたとき、検証不能になる。
比較可能であり続けるには、意思決定は次の束を一緒に運ばなければならない。

* **Basis** — 何を読んだか。客先図面、仕様書、過去案件 ID など。これが欠けると、その選択を正当化できない。
* **Conditions** — どの前提のもとでか。取り付け方向、測定軸、環境、選択したルールセットなど。これが欠けると、同じ部品なのに違う結果が生まれる。
* **Effects** — どの外部依存が結果に影響したか。表、辞書、モデル、道具の版など。これが欠けると、ドリフトが人間のミスに見える。
* **Evidence** — あとで再確認し、それを同等な決定として受け入れるために必要なだけの記録。これが欠けると、再確認そのものができない。最小限でいえば、basis や入力へのポインタ、依存の版、短い commit 理由を一か所に置くことが必要になる。
* **Approvals** — 誰が、どの段階で commit を承認したか。これが欠けると、commit 権限が曖昧になる。

（Observation Point Design エッセイでは、前提条件と外部要因はもう少し圧縮された形で導入されている。ここで Conditions と Effects を分けるのは、現場実務に合わせたものである。取り付け方向や測定軸と、lookup table の版では、壊れ方が異なり、別々に診断する必要があるからだ。）

これらが散らばっていると、もっともらしいが比較できない出力が生まれる。
これらが一緒に運ばれていれば、同じ宣言済み条件のもとでワークフローを再点検し、その結果を同等なものとして受け入れ直すことができる。

**contract** とは、ある決定種別について、その束が何を含まなければならないかを宣言するものである。
**gate** とは、commit の前にその束を確認し、不足があればオペレータを recovery へ送る stop point である。
recovery とは、四つの問いに答えることである。何が欠けているのか。どこでそれを得るのか。先へ進むための最小の修正は何か。それが得られないとき、どこへエスカレーションするのか。

これらはまったく新しい発想ではない。
経験のある現場担当者の多くは、すでに頭の中にその変種を持っている。
要点は、それを明示的で、確認可能で、持ち運び可能な形にすることにある。
そうすれば、人の入れ替わり、道具の移行、AI の導入をまたいでも生き残る。

## 6. その性質を設計に接続する

「なぜ VBA が機能するのか」と「次に何を設計すべきか」は、直接結びつけて考えられる。

| Excel 上の VBA の性質  | 設計プリミティブ             | それが答える問い                    |
| ----------------- | -------------------- | --------------------------- |
| データへの近さ           | 参照束                  | 必要な basis は散逸せず、意思決定に付いているか |
| 配布の単純さ            | Contract 梱包          | ツールと前提条件を、検証可能な一単位として配布できるか |
| Human-in-the-loop | Gate と recovery path | 人が commit 前に止まり、誘導付きで再開できるか |
| 暗黙の契約             | Contract の明示化        | 前提条件は宣言され、自動で確認できるか         |

目的は VBA を守ることではない。
Excel 上の VBA が、時に偶然に、時にそれを保守してきた人たちの蓄積された知恵によって守っていた、運用上の不変条件を守ることである。

## 7. 本当に測るべきものを測る

もし AI を「どれだけ速く答えを出すか」で測るなら、最適化の対象を間違える。
現場がお金を払うのは答えに対してではない。
安定した意思決定に対してである。

雑音を切り裂く指標は二つある。

**Comparability rate**
同じ宣言済み basis と conditions のもとで、結果はどれくらいの頻度で同等なものとして戻ってくるか。
完全な再現性は必要ない。
必要なのは、見える形で境界づけられたドリフトである。
ドリフトが見つかったら、システムは静かに続行するのではなく、止まり、再承認を要求しなければならない。

**Human-in-the-loop cost**
ためらい、説明、手戻りにかかる総コストである。
レガシー環境では、まず記録しやすいものから始めればよい。

* 差し戻し。再提出を必要とする正式な却下
* 理由探し時間。なぜその結果が受け入れ可能かを再構成するのに使った時間
* 承認待ち。承認から commit までの境界で止まっていた時間
* 生成後修正。自動出力のあとに人手で入れた修正

差し戻しだけを追うだけでも、どこで意味論が不安定かを示す先行指標になる。
そのおかげで、プラットフォーム全体を作り直さなくても、問題は行動可能になる。

---

## 結び：速さは comparability のあとに来る

Excel 上の VBA が機能し続けるのは、それが現代的だからではない。
それは、現代のシステムがしばしば忘れてしまうこと——意思決定は stoppable で、recoverable で、comparable でなければならない——を静かに強制しているからである。

Excel 上の AI がその場所を得るのは、同じことができるようになったときである。
より賢くなることによってではなく、束を運び、contract を確認し、不足があれば gate で止まることによってである。

明日から始めたいなら、三つだけやればよい。

1. 失敗しやすい commit 境界を一つ選び、その前提条件を contract として書き出す。
2. commit 前に止まり、何が欠けていて、どう recover するかをオペレータへ伝える gate を追加する。
3. 今日から記録できる指標を一つだけ取る。差し戻しか生成後修正でよい。そして毎週それを見直す。

小さく始めること。
速さは comparability のあとに来る。
